# TNH Scene Compiler — Project Instructions

## Overview

Fountain-TNH scene compiler: converts `.scene` files to Ren'Py `.rpy` scripts for The Null Hypothesis game. Three packages:
- `tnh_scene_compiler` — main compiler (CLI + GUI)
- `tnh_refresh_allowlists` — allowlist extraction from TNH source (characters, faces, moods, traits, personalities, history events, etc.)
- `tnh_generate_cheatsheet` — markdown cheatsheet generator

## Architecture

- **Config**: `tnh_scene_compiler.<prefix>.yaml`, loaded via `config.py`. Legacy `tnh_scene_compiler.yaml` supported.
- **Pipeline**: parse → DSL transform → validate → codegen.
- **Output**: pluggable callback system (`output.set_callback`) for CLI/GUI.
- **GUI**: Tkinter, wizard flow (Welcome → Quick/Project/Init screens), threaded compilation.
- **DSL**: `dsl.py` transforms writer-friendly syntax to canonical Ren'Py calls. Project aliases via `aliases.yaml`.
- **Condition Builder**: `condition_builder.py` — guided dialog for building `[[if]]` condition expressions from any number of clauses (each after the first joined with and/or via its own operator; "+ Add condition" / "Remove"). Per-clause UI lives in `_ConditionClausePanel`, whose type selector is two-level (Category -> Condition) built from `build_condition_catalog` (built-in checks + allowlist functions grouped/labelled; a promoted function jumps straight to its param form). The dialog holds a scrollable list of clauses. **Per-parameter widget selection**: a function/method parameter is rendered by `_build_param_field` according to `param_widget_kind` — a declared `param_choices` value (loaded per entry into `condition_function_param_choices` / `character_method_param_choices`) → editable combo, resolved by `resolve_param_choices`: either a fixed list (fx-style) or a dynamic `{source, quote, suffix}` mapping pulling a named allowlist set (`history_events`, `characters`, …) at render time so suggestions stay in sync (e.g. `Item` → every history event, quoted); a single `Character` → readonly picker; a `Character` collection (`is_character_collection_param`: a `Characters`/`*_Characters` name — the allowlist strips the type, so the name suffix catches `arriving_Characters` — or a container type) → a checkbutton multi-select picked in a dedicated window (`_build_character_set_widget` shows a `Choose… (N)` button; `_open_character_set_picker` opens the modal picker; the shared `char_vars` persist the selection), assembled into a set literal via `format_character_set` (`{JeanGrey, Rogue}` / `set()`); a single location (`is_location_param`: bare `Location`/`location` or a `Location` type) → `_build_location_widget`: a "Current location?" toggle (default on, hides the slugline combo) — for a *required* location it inserts `get_Location()`, for an *optional* one (`omit_when_current`, i.e. the param has a default) the trailing arg is dropped by `_join_args`/`_is_omitted_location` so `get_Location()` never nests into `get_Location(get_Location())`; unticked reveals an editable combo of the known sluglines inserted **quoted**; a `bool` → `True`/`False` combo; a `(day, time_index)` date (`is_date_tuple_param`, `tuple[int, int]`) → `_build_date_widget`: a Day number + a named time-of-day dropdown (`_TIME_PERIODS`) assembled into `(day, index)`; else free text. Help text (built-in `_DESCRIPTIONS` and per-entry `notes`) is reflowed through `flow_text` and shown in `wraplength`ed labels so hand-wrapped source lines don't fight the label's own wrapping. Pure-logic helpers (`build_condition`, `build_condition_catalog`, `join_conditions`, `resolve_method_path`, `wrap_condition`, `param_widget_kind`, `is_bool_param`, `is_date_tuple_param`, `format_character_set`, `resolve_param_choices`, `flow_text`) are testable without Tkinter.
  - **"Advanced" holds exactly one entry: "Character method (any)".** The generic "Standalone function (any)" picker was removed and must not come back: `build_condition_catalog` promotes *every* allowlist function to its own named entry (an uncategorised one falls to "Advanced"), so the generic path reached nothing new — it re-listed the same functions under their raw names, grouped by the raw allowlist `category` field, i.e. a second taxonomy conflicting with the top-level one ("Approval" there vs "Relationships" here). `_params_function` is therefore always the preset path. Character methods keep their generic picker — they are never promoted individually, so it is their only access.
  - **`_SUGAR_DUPLICATE_FUNCTIONS` holds only exact duplicates**, currently just `Character_is_in_close_proximity` (the Nearby check takes the same single argument). `check_approval` and `are_Characters_friends` were listed there too and had to come back out: each built-in reaches a strict *subset* — one axis against a literal number vs. combined love+trust and named thresholds; two characters at tier 1 vs. any number at any tier. Before adding a name here, check the built-in covers the function's whole surface, not just its common case.
  - **Every declared parameter is emitted into the call** (`_join_args` only drops a trailing omitted location), so an allowlist signature is a *curated* surface, not a mirror of the source: declaring `check_approval`'s `extra_condition` / `multiplier` / `default` would write them into every call for no gain. For the same reason a parameter with no declared default emits an empty argument, so `is_valid` refuses to insert while any signature field is blank, and a `Character` field pre-selects the first character.
  - Both pickers go through the same `_build_param_field` as a promoted function, so widget work needs no plumbing to reach Advanced; what a method is missing is only its `param_choices` **data**.
  - **Don't spend `param_choices` on a method a built-in already compiles to.** `check_trait`, `check_personality`, `get_status` and `is_in_normal_mood` are the Trait / Personality / Mood checks (`dsl.py`), and `get_friendship` is "Opinion of another (tier)"; guiding the raw form duplicates the friendlier one. Wire the ones a built-in *cannot* express — `History.check` beyond `.did`'s fixed `> 0` on the persistent tracker, `History.check_when`, `get_trait`'s value read. The entries stay listed either way: the generic picker is the escape hatch, per the same reasoning that keeps the allowlist browser writable.
- **New Scene Dialog**: `new_scene_dialog.py` — guided form for creating scenes with setup fields (title, character, scene type, trigger, location) and 4 example templates. Pure-logic helper (`build_scene_text`) testable without Tkinter.
- **Glossary**: `glossary.py` — a non-modal reference window (editor toolbar "Glossary" button) with a searchable section list + copyable code examples, parsed at runtime from the bundled `docs/glossary/*.md` files (one per top-level section, numbered for order; read in name order, concatenated, then parsed). Prose/notes render in a read-only `Text` widget so inline `[label](#section-slug)` cross-reference links are clickable (jump to that section). Pure parser (`parse_glossary`) + `slugify` / `parse_inline_links` testable without Tkinter; the glossary folder is in the `.spec` datas.
- **Allowlists**: two-layer (base + project), loaded in `allowlists.py`, validated in `validator.py`. **Anything that reports what a writer may type must read both layers** — a project's own allowlists may legitimately hold only what it adds, with the game's values coming from `allowlists_base`. `tnh_generate_cheatsheet` gets this via `loader.load_layered()`; the mod repo's `Tools/generate_test_scenes` takes a list of layer directories for the same reason. A new single-layer consumer would silently drop the whole base game. Separate on disk, merged in memory: `merge()` unions the layers at validation time (one scene legitimately names `[Player.name]` and a mod character), and that union is never written back.
- **`include_tnh` is what tells the two layers apart.** `allowlists_base` is the output of a refresh run *with* it (against the game, no mod); a project layer is the output of a run with `--no-include-tnh` (the mod alone). So an extractor's hardcoded/engine values — `Player` + `Narrator` in `characters.py`, the look baseline in `looks.py`, the Player/world paths in `interpolation.py` — must be gated on `context.include_tnh`: emitting them unconditionally copies game values into every project's own files. Values an extractor *discovers* are not gated; they carry the real path they were found at (see `_discover_character_tags`), which is what `classify_origin` needs to place them.
- **A slugline maps to exactly one location.** It is derived from the location's `name`, and TNH has locations sharing one (`loc_PlayerShower` carries the bedroom's name). `locations.py` emits a slugline once — first declaration wins, collision reported as a warning — because `_build_location_map` is a plain dict and would otherwise hand the writer whichever entry was read last. The loser gets a slugline of its own in `locations_overrides.yaml`; that file is also the escape hatch for `.copy()`-declared locations the extractor skips.
- **Allowlist browser**: `allowlist_browser.py` — a non-modal window (buttons on `ProjectScreen`, `QuickScreen`, and the editor toolbar). Callers without a `Config` (quick mode) pass `default_base_dir()` and `project_dir=None`, so the window is base-only and read-only there.
  - **Two axes, do not conflate them.** *Origin* (`ORIGIN_CORE` / `ORIGIN_PROJECT`) is per **value** and drives the sidebar split and editability (`is_editable_in` — the project side is always editable, the core side never). *Maintenance* is per **file** and is purely informational: `survives_refresh` decides whether saving warns. They cross freely — `condition_functions.yaml` is refresh-safe yet holds game-origin values from the base layer.
  - **Do not re-lock the generated files.** `tnh_refresh_allowlists` needs an extracted base game; a project that cannot run it has no other way to fill an allowlist, and the compiler's `merge()` carries every field (including `character_methods` / `character_properties`, which have no extractor at all). The overwrite risk is surfaced — inline warning plus a one-per-list `askokcancel` on save, tracked in `_warned_keys` — not prevented.
  - `classify_origin` is the rule: base layer → always core; project layer → compare the entry's `source_file` root against `base_game_root` / `project_root` from that layer's `_meta.yaml`, with `_CORE_SENTINEL_ROOTS` (`<builtin>`, `game`) counting as core and anything unplaceable (no source, `manual`) falling to project. A generated file legitimately holds both.
  - `ALLOWLIST_TOPICS` is the catalogue; `maintenance` is `generated` (rewritten by `tnh_refresh_allowlists`), `manual` (the 5 files the refresh preserves — assert-locked by a test against `_MANUAL_SCAFFOLDS`), or `developer` (hand-maintained in the base layer). `is_editable_in(origin)` is the only editability gate; `blurb(origin)` is the per-side explanation.
  - Editing is raw YAML so the files' hand-written header comments survive a save (a `safe_load`/`safe_dump` round-trip would delete them), gated by `validate_topic_yaml`.
  - **Performance is load-bearing here** — a full read is ~100 YAML files and the sidebar needs it at open. Three things keep it at ~180 ms: the libyaml `CSafeLoader` (7x, with an `ImportError` fallback), `_META_CACHE` (`_meta.yaml` was over half of all parses), and `_groups` reading each list once and splitting both sides in memory. Do not reintroduce a per-origin read. `Reload` drops `_groups_cache`, `_name_index`, and the meta cache.
  - Pure helpers (`classify_origin`, `read_layer_meta`, `load_topic`, `read_layer`, `topic_characters`, `topic_path`, `validate_topic_yaml`) are testable without Tkinter.

## Naming Conventions

- `project_prefix` (not `mod_prefix`) — used everywhere in code, config, and YAML.
- `project_allowlists` (not `mod_allowlists`), `project_root` (not `mod_root`).

## Testing

- Framework: pytest
- 681 tests in `tests/`
- Run: `python -m pytest tests/ -q`

## Thumbnails

- **Import**: `python scripts/import_thumbnails.py <path-to-TNH-VisualReference>` reads face/arm PNGs, resizes via Pillow, outputs to `thumbnails/` with `_mapping.yaml`.
- **Runtime**: `tnh_scene_compiler/thumbnails.py` — `ThumbnailStore` singleton, lazy-cached `tk.PhotoImage` objects. No Pillow at runtime.
- **GUI**: previews in `_CharacterInsertDialog` (column 2), `_DirectiveDialog._build_show` (column 2), `_PaletteSidebar._refresh_visuals` (compound buttons for Faces/Arms).
- **Settings**: `show_thumbnails: bool` in `AppSettings` (default `True`).
- **Bundle**: `thumbnails/` included in PyInstaller `datas` in `.spec`.
- **Mapping keys**: face names match allowlist names; arm keys are prefixed with `both_`/`left_`/`right_`.
- **Fuzzy matching**: the import script handles typos in source filenames (e.g. `appaled` → `appalled`).

## Build

- PyInstaller: `pyinstaller tnh_scene_compiler.spec`
- Release: push a `v*` tag to trigger `.github/workflows/release.yml`
